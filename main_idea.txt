# SIGNAL//LOST — Game & App Concept

## Core Idea

SIGNAL//LOST is a small mystery/puzzle game that takes place entirely inside a fictional computer operating system.

The player works at a signal-monitoring research station. Their job is normally simple: monitor incoming data and investigate unusual transmissions.

One day, the system detects an unknown signal.

At first it looks like a strange transmission coming from somewhere far away.

The player begins investigating it.

The entire game is played through the computer interface.

There is no character walking around, no 3D environment, no combat system and no complicated character animations.

The computer itself is the game world.

---

# Main Goal

The objective is NOT to collect codes or simply complete random puzzles.

The player's overall goal is:

**Investigate the unknown signal, understand what is communicating with the station, discover where the signal originates, and ultimately decide what to do with it.**

The player initially believes they are investigating a strange signal from space.

As the game progresses, evidence begins contradicting that assumption.

Eventually, the mystery becomes much larger:

**What is actually communicating with me?**

**Why does it understand this computer?**

**Why were previous researchers investigating it?**

**Why was the research stopped?**

**And should I continue communicating with it?**

---

# General Gameplay

Most gameplay happens through several applications on a fictional desktop.

The player switches between applications, investigates information and gradually connects clues.

The core loop is roughly:

**Receive something unusual → investigate → search files/data → understand a clue → perform an action → discover new information → progress the mystery.**

The important part is that the player should feel like THEY figured something out.

The game shouldn't constantly tell them:

"Go to Files."

"Now open this."

"Now enter this."

Instead, information found in one application should make something in another application suddenly make sense.

---

# The Computer

The player uses a fictional modern operating system designed for a research station.

It should NOT look like Windows 95 or an old CRT computer.

It should feel like modern specialist software used in a scientific facility.

The desktop might contain applications such as:

* Files
* Terminal
* Signal Receiver
* System Status

Later, additional applications can appear:

* Signal Decoder
* Network Monitor
* Firewall
* Communications
* Archive
* Diagnostics

Some applications may not exist at the beginning.

Discovering something during the story can unlock a new application.

That means the computer itself gradually expands as the player progresses.

---

# Visual Direction

The UI should be modern, dark and minimal.

Think:

**modern research software + mystery game + developer tools**

rather than:

**retro hacker computer**

Possible characteristics:

* dark background
* clean modern typography
* subtle borders
* slightly transparent panels
* soft shadows
* restrained glow
* modern icons
* lots of spacing
* clear information hierarchy
* subtle cyan/blue/green accent colours
* smooth hover states
* small status indicators
* clean charts/data displays
* modern terminal design

The terminal should look closer to a modern developer terminal than an old green CRT screen.

For example:

```text
SIGNAL//TERMINAL

station@signal-03  ~

> _
```

It should feel believable but fictional.

The game does not need lots of animation.

Small effects can eventually be used for atmosphere:

* terminal cursor blinking
* incoming signal indicator
* notification appearing
* window opening
* tiny loading indicators
* signal waveform moving
* warning state
* screen interference during important moments

These should be polish, not core mechanics.

---

# Beginning of the Game

The player starts on the research station desktop.

Everything appears normal.

There are only a few applications available.

The player can explore the system and read some basic information about the station.

Eventually, either automatically or through using the system, an unusual signal is discovered.

The Receiver reports something it cannot identify.

This begins the mystery.

---

# Signals

Unknown transmissions are initially difficult to understand.

They may contain unfamiliar symbols, patterns or strange pieces of data.

The player gradually learns how to interpret them by investigating:

* previous research
* archived files
* logs
* patterns between transmissions
* information hidden elsewhere on the computer

The signals should gradually evolve.

At first:

Completely incomprehensible.

Later:

Small parts become understandable.

Eventually:

The player realizes that whatever is communicating is also learning how to communicate with THEM.

This progression should make communication feel increasingly personal.

---

# Files & Investigation

Files are one of the main storytelling tools.

The player can discover:

* research reports
* previous operator notes
* signal recordings
* system logs
* abandoned experiments
* classified information
* corrupted files

Some information may appear meaningless when first discovered.

Later, another clue makes the player remember:

"Wait... I saw something about this earlier."

The player returns to that file and suddenly understands its importance.

This encourages investigation rather than simply following objectives.

---

# Terminal

The terminal is another important part of the game.

It is NOT a real operating-system terminal.

It is a fictional game terminal with a limited set of commands.

The player can use it to interact with station systems.

Over time, new commands or capabilities may become available.

The terminal should make the player feel like they are directly operating the research station while remaining simple enough to implement in React.

---

# Unlocking Things

Progression can physically change the computer.

For example, solving something might:

* unlock a previously inaccessible file
* reveal a hidden folder
* install/unlock a new application
* enable another terminal command
* reveal another frequency
* restore corrupted information
* enable another system

This gives the player a clear feeling of progress without needing traditional RPG systems.

The desktop they have near the end of the game could be noticeably more capable than the desktop they started with.

---

# Editing / Creating Files

Later in the game, the player may need to interact with files rather than only reading them.

For example:

* edit text
* add information
* create a file
* rename something
* move something
* delete something

A transmission might indirectly communicate that a certain action is required.

The player has to understand the instruction and perform it using the computer.

This should feel like the unknown signal is communicating through the operating system itself.

---

# Security / Hacking Events

Later, unusual network activity begins appearing.

Something may attempt to access the station.

This creates occasional hacking/security events.

These should NOT be realistic cybersecurity simulations.

They are simple fictional minigames.

For example, the player might have to quickly identify and block suspicious connections, match a short sequence, route a connection correctly, or close vulnerable nodes.

The purpose is to:

* break up investigation gameplay
* create tension
* make the computer feel alive
* create consequences

These events should be occasional rather than constant.

---

# Failed Security

Failing a security event should not simply produce:

GAME OVER.

Instead, something interesting can happen.

A file might become corrupted.

A system setting might change.

Something new might appear.

A log might be modified.

The player then has to determine what happened.

This turns failure into part of the mystery.

---

# The Mystery Develops

Initially, the player assumes:

"We found an unusual signal."

Then:

"The signal seems intelligent."

Then:

"It understands our responses."

Then:

"It seems to understand the computer."

Then:

"Something has been communicating with this station before."

Old files reveal that previous researchers encountered the same phenomenon.

Research was stopped for reasons that are initially unclear.

Eventually the player discovers something disturbing:

The signal may not originate where everyone assumed it did.

This becomes the central mystery of the game.

---

# Trust

As communication improves, the unknown entity may begin giving the player instructions.

At the same time, the station's own security systems may warn the player against following them.

This creates a conflict:

**Do I trust the station?**

or

**Do I trust the signal?**

Neither side should immediately be obviously correct.

The player discovers evidence and makes their own judgement.

---

# End Goal

Near the end, the player finally gains the ability to trace the signal properly.

Everything they've discovered leads toward answering the main question:

**Where is it coming from?**

The result reveals that the situation is not what the player originally believed.

The exact story can be developed later, but the signal may turn out to be connected to the station itself, previous experiments, another system, another reality, or something even stranger.

The important part is that the answer changes how the player understands everything that happened earlier.

---

# Final Decision

The game ends with a meaningful choice involving the connection.

For example, conceptually:

**Terminate the connection**

or

**Allow the connection to complete**

The exact choice can change as we develop the story.

Different choices can produce different endings.

We do NOT need many endings.

Two strong endings are enough for a small game.

---

# Game Structure

The game can be thought of as several transmissions/chapters.

### Chapter 1 — Discovery

The player discovers the unknown signal.

They investigate their first strange transmission and successfully establish communication.

This is also our first development prototype.

---

### Chapter 2 — Communication

The player begins understanding pieces of the signal.

The signal begins reacting to the player's actions.

---

### Chapter 3 — Investigation

Old research reveals that this phenomenon has happened before.

The player starts questioning the supposed origin of the signal.

---

### Chapter 4 — Interference

Security problems begin.

Files or systems behave strangely.

The player is no longer sure whether the station itself can be trusted.

---

### Chapter 5 — Origin

The player finally traces the signal.

The central mystery is revealed.

The player makes the final decision.

Game ends.

---

# Scope

Although the full concept sounds large, development should remain SMALL.

We are not building all five chapters immediately.

Development starts with:

**Chapter 1 only.**

Chapter 1 should essentially be a short playable prototype.

The first goal is simply:

**Open computer → explore → discover signal → investigate → solve one small puzzle → establish communication → end prototype.**

If that works and is enjoyable, Chapter 2 can be designed.

This prevents the project from becoming too large for a first personal Next.js project.

---

# Technical Philosophy

This is primarily a learning project.

The game should be designed around things that are natural to build with Next.js and React:

* components
* state
* forms
* buttons
* text inputs
* arrays
* objects
* conditional rendering
* file-like data
* application windows
* simple game progression
* localStorage later
* CSS/Tailwind styling

Avoid systems that require:

* complex physics
* 3D graphics
* complicated animation
* multiplayer
* real networking
* real hacking functionality
* large databases
* complicated backend infrastructure

The illusion should be more complex than the actual implementation.

A mysterious "research operating system" might look complicated to the player while underneath it is simply React components responding to state.

That is one of the main design principles of SIGNAL//LOST.

---

# Design Principle

The player should frequently experience:

**"Wait... I think I know what this means."**

Not:

**"The game told me exactly what button to click next."**

Mystery, discovery and connecting information are the core of the game.

The signals, terminal, files, security events and fake operating system all exist to support that feeling.
